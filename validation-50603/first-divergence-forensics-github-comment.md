@cadamcat I instrumented the first divergent greedy token on the W7900D TP=1 reproducer (your harness semantics, Muse/512/eager, vLLM 0.25.1). The sampler is not where the two runs first diverge: the logits feeding argmax are already numerically different while the token histories are still identical, and offline argmax on the saved logits reproduces each run's winner. And the difference is not near-tie sized — the forward pass itself varies run-to-run by more than the decision margins.

One concrete pair (of 28; all 8 generations pairwise divergent, 8/8 unique in this engine): at generated step 11, runs 0 and 1 have identical histories through step 10, then run 0 picks token 112740 (logit 69.0, runner-up 200007 at 67.0, margin 2.0) while run 1 picks 200007 (67.5 vs 67.0, margin 0.5). The two full argmax-input logits rows differ by up to 2.7 logit units across the vocabulary. Offline CPU and GPU argmax of the saved rows (20× each, fresh process) are deterministic and match vLLM's selection for every pair; the probe's own argmax agrees with the engine at all 512 instrumented steps.

Scale check that kills the near-tie story: at aligned positions where all runs still share identical histories, cross-run logits differ by up to 8.8 (median 3.25), while the top1-top2 margins at the divergence points are 0–2.0 (median 0.5). The variation exceeds the margins — Category B in our classification, i.e. the divergence is materially present in the forward pass before sampling, not argmax jitter on ties.

Pushing upstream one layer: with a gated identity hook on the LM-head layer, the final hidden states entering the LM head already differ — all 8 generations produce 8 distinct hidden-state hashes at every decode step, including step 0 right after the shared prompt. Call counting proves every measured generation hit the shared prefix cache (520 LM-head calls = 8 warm-up + 8×64 measured, zero prefill recomputes), so those steps run with identical inputs and weights. Eager mode rules out torch.compile.

Then the micro-probe: `torch.ops._rocm_C.gptq_gemm_rdna3` (`RDNA3W4A16LinearKernel`) called in isolation through vLLM's own test-recipe layer, with the real layer-0 q_proj weights (K=6656, N=4096, group 128) and a fixed seeded bf16 input, is not bit-repeatable: at the decode shape M=1, 100–200 repeated calls produced 100–200 distinct outputs in each of three processes (max |Δ| vs first call 0.047–0.078), and even the first call's output differs process-to-process; at prefill shape M=128 it settles into 2 variants per process. That matches the end-to-end picture exactly — decode steps (M=1 GEMMs) vary maximally, the cached prefill (M=128-class) is stable enough to be shared.

So the current boundary is: sampler/logits-processing/argmax exonerated; the origin is the decode-shape invocation of the RDNA3 W4A16 GEMM on gfx1100, nondeterministic on fixed inputs in isolation. The mechanism inside that kernel is the open question — and this stays compatible with your kernel probe, which cleared the Triton paged-attention kernel, a different kernel from this one.
